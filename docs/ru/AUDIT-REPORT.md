## 3. Экосистемная конфигурация

### 3.1 Docker

| Пункт конфигурации | Service | Admin | Статус |
|--------|---------|-------|------|
| Dockerfile | ✅ базовая версия | ✅ полная версия | ⚠️ см. ниже |
| docker-compose.yml | ✅ | ✅ | ⚠️ см. ниже |
| .env.docker | ❌ | ✅ | — |
| Конфигурация Nginx | ❌ | ❌ | ⚠️ см. ниже |

**Детали проблем**:

1. **Dockerfile Service неполный** — установлены только `pdo, pdo_mysql, pcntl`, отсутствуют:
   - `gd` (генерация изображений капчи poster-php)
   - `mbstring` (многобайтовые строки)
   - `redis` (подключение к Redis)
   - продакшен-конфигурация `opcache`

   При этом admin Dockerfile устанавливает все расширения и настраивает OPcache полностью.

2. **Admin docker-compose ссылается на несуществующую конфигурацию Nginx**:
   ```yaml
   # admin/docker-compose.yml line 20
   - ./docs/nginx-security.conf:/etc/nginx/conf.d/security.conf:ro
   ```
   Каталога `admin/docs/` нет, файла `nginx-security.conf` нет.

3. **В Service docker-compose у контейнера Nginx нет монтирования конфигурации** — смонтирован только `./public`, конфигурация nginx не смонтирована, работать не может.

4. **У Service отсутствует `.env.docker`** — у admin есть отдельный файл переменных для Docker, у service нет.

### 3.2 Миграции БД

| Проект | Файлы миграций | Статус |

| Service | ❌ нет отдельного каталога миграций | только `seed.php` |
| Admin | ✅ 8 SQL-файлов миграций | `database/migrations/` |

У Service нет официального механизма миграций БД, создание структуры таблиц зависит от seed.php или ручного выполнения.

### 4.2 Дисбаланс слоя моделей

У Admin всего 7 моделей против 58 у Service. Большинство из 54 контроллеров Admin выполняют операции, требующие доступа к таблицам БД (заказы, пользователи, мастера и т.д.), но соответствующие Eloquent-модели не определены. Предположительно Admin обращается к Service через API, а не напрямую к БД. Если так, Admin следует позиционировать как «шлюз фронтенда», а не как независимый бэкенд.

### 4.3 Конфигурация безопасности — отлично

В `service/config/security.php` настроены **31 детектор атак**, покрывающие OWASP Top 10 и больше:
- XSS, SQL-инъекции, инъекции команд, обход путей, SSRF, XXE
- JWT-атаки, атаки на Host-заголовок, Request Smuggling, GraphQL-инъекции
- JNDI-инъекции, SSTI, NoSQL-инъекции, CSV-инъекции
- Prototype Pollution, WebSocket-атаки, CORS, DNS Rebinding
- Автоматическая блокировка по IP-чёрному списку (5 раз/60 сек → блокировка 15 минут)

Все детекторы по умолчанию в режиме `block`, немногие в режиме `log` (`header_injection`, `ssti`, `nosql_injection`).

### 4.4 Шифрование чувствительных полей — настроено

Трейт `Encryptable` применён к ключевым моделям:
- User: `phone`, `wx_openid`, `wx_unionid`, `real_name`
- TechnicianProfile, Store, UserAddress, TechnicianWithdrawal и др.

### 4.5 Проектирование маршрутов — хорошо

- ✅ Версионирование API через заголовок запроса `API-Version` (не через путь URL)
- ✅ Слоистость middleware: ApiVersion → Auth → TechnicianAuth (постепенное ужесточение)
- ✅ Маршруты платёжных колбэков отдельные, без middleware Auth
- ✅ Разрешение версионированных контроллеров через замыкание `v()`
- ✅ `Route::disableDefaultRoute()` предотвращает неопределённые маршруты

### 4.6 Стиль кода
- ✅ Стандарт PSR-12
- ✅ `declare(strict_types=1)` — строгая проверка типов
- ✅ Middleware JWT Auth реализует `MiddlewareInterface`
- ✅ Модели используют Eloquent ORM + SoftDeletes
- ✅ Единообразное использование распределённых ID Snowflake

## 8. Раунд усиления безопасности 2026-08-26

Подробности — в восьмом разделе [SECURITY-AUDIT-REPORT.md](SECURITY-AUDIT-REPORT.md).
